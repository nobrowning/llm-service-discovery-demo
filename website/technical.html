Overview总览

Two separate paths connect a client to a service. Discovery uses multicast DNS on the local link and only carries connection hints. The API itself is reached over a direct HTTPS connection, after the user chooses the service. The advertiser and the discovery client never proxy API requests.

客户端和服务之间有两条独立的路径。发现使用本地链路上的组播 DNS，只携带接入线索。用户选择服务后，客户端通过直接的 HTTPS 连接访问 API。公告器和发现客户端都不转发 API 请求。

Service type and records服务类型与记录

Services use the DNS-SD service type _llm-api._tcp.local. The _tcp label describes how the API is reached. Discovery messages themselves travel over UDP multicast. The service type is proposed by the draft and is not yet registered with IANA.

服务使用 DNS-SD 服务类型 _llm-api._tcp.local.。其中 _tcp 描述的是访问 API 的传输方式，发现报文本身通过 UDP 组播传输。该服务类型由草案提出，尚未在 IANA 注册。

Four record types together describe one endpoint. A client reads them in this logical order. In practice several records can arrive in one packet or come from cache.

四类记录共同描述一个接入点。客户端按下面的逻辑顺序读取；实际中多条记录可能在同一个报文中到达，也可能来自缓存。

  1. PTRWhich instances exist?有哪些实例？Service type → instance names服务类型 → 实例名
  2. SRVWhere is it?服务在哪里？Instance → host name and port实例 → 主机名和端口
  3. TXTHow is it used?如何使用？Scheme, base path, API profile, auth hintscheme、base 路径、API profile、认证提示
  4. A / AAAAWhich address?连接哪个地址？Host name → IP address主机名 → IP 地址
; One service, as published by the advertiser (TTL 120 s by default)
_llm-api._tcp.local.                  PTR  Office-DeepSeek._llm-api._tcp.local.
Office-DeepSeek._llm-api._tcp.local.  SRV  0 0 8443 api-office-a.local.
Office-DeepSeek._llm-api._tcp.local.  TXT  "txtvers=1" "api=openresponses" "protovers=2026-04-24"
                                           "scheme=https" "base=/v1" "auth=required"
api-office-a.local.                   A    192.168.10.21

Resulting endpoint组合得到的接入点

https://api-office-a.local:8443/v1

POST https://api-office-a.local:8443/v1/responses

The URL is scheme://SRV-target:SRV-port + base. The base path is always taken from the record and never assumed to be /v1. One host can publish several services, for example /text/v1 and /vision/v1 on the same port. Each is its own instance with its own key policy, so a client must never merge services by IP address.

URL 由 scheme://SRV 目标主机:SRV 端口 + base 组成。base 路径始终从记录中读取，不会默认补成 /v1。同一台主机可以发布多个服务，例如同一端口上的 /text/v1 和 /vision/v1。它们是各自独立的实例，各有自己的 key 策略，所以客户端不能按 IP 地址合并服务。

TXT keysTXT 字段

The TXT record stays small. It holds only what is needed to build and interpret the endpoint.

TXT 记录保持精简，只包含组成和理解接入点所需的信息。

  • 字段名不区分大小写；同一字段出现两次时取第一个值；未知字段忽略。
  • Host and port belong in SRV, and addresses in A/AAAA. They are not repeated in TXT.
  • 主机名和端口在 SRV 中，地址在 A/AAAA 中，不在 TXT 中重复。
  • Keys, prompts, model catalogs and hardware details never go in TXT. Model details are read later over HTTPS.
  • key、提示词、模型目录和硬件信息都不放进 TXT。模型详情之后通过 HTTPS 读取。

Discovery flow发现流程

From a service starting up to a request reaching it. Steps 1 to 6 happen automatically. Steps 7 and 8 happen only when the user acts.

从服务启动到请求到达服务的全过程。第 1 到 6 步自动完成，第 7、8 步只在用户操作时发生。

  1. Advertiser公告器Probe for conflicts探测名称冲突

    Before announcing, the advertiser asks whether its instance and host names are already in use. A conflict stops startup instead of silently renaming the service.

    公告之前，公告器先查询实例名和主机名是否已被占用。发生冲突时停止启动，不会悄悄给服务改名。

  2. Advertiser公告器Announce and answer公告并应答

    It sends its records twice at startup, then answers matching queries. Known-answer suppression avoids repeating what a client already has. Records live for 120 seconds by default.

    启动时发送两次公告，之后应答匹配的查询。已知答案抑制（known-answer suppression）避免重复发送客户端已有的记录。记录默认有效期为 120 秒。

  3. Client客户端Browse浏览

    The discovery core joins 224.0.0.251:5353 on one selected IPv4 interface and queries PTR _llm-api._tcp.local. It repeats the query periodically (every 10 seconds by default) and refreshes records before they expire.

    发现核心库在选定的一张 IPv4 网卡上加入 224.0.0.251:5353，查询 PTR _llm-api._tcp.local.。它会定期重复查询（默认每 10 秒），并在记录过期前刷新。

  4. Client客户端Resolve解析

    For each instance it collects SRV, TXT and A/AAAA from answers and its cache, and asks for any record that is still missing.

    对每个实例，从应答和缓存中收集 SRV、TXT 和 A/AAAA 记录，缺少的记录会再发查询。

  5. Client客户端Validate and build the endpoint校验并组合接入点

    Once the records are complete, it checks the TXT keys, host name, port and addresses (see Candidate validation) and builds the base URL. Invalid candidates are reported but never become connectable.

    记录凑齐后，检查 TXT 字段、主机名、端口和地址（见候选校验），并组合出 base URL。无效候选会被报告，但不会成为可接入的候选。

  6. Client客户端Keep a live candidate list维护候选列表

    Each candidate carries its instance name, base URL, addresses, auth hint, network attachment, expiry time, validation result and a generation number, so the app can reject a stale selection. Subscribers receive added, updated, invalid, removed, network, status and warning events (network from 0.4.0-roaming.1).

    每个候选包含实例名、base URL、地址、认证提示、网络附着信息、过期时间、校验结果和代次号，应用可以据此拒绝过时的选择。订阅方会收到 added、updated、invalid、removed、network、status 和 warning 事件（network 事件自 0.4.0-roaming.1 起提供）。

  7. User用户Inspect检查服务

    Only when the user asks, the client checks its local trust settings and the TLS certificate, then reads GET {base}/models and GET {base}/_llm/capabilities. Discovery by itself sends no API request.

    只有在用户要求时，客户端才会检查本地信任设置和 TLS 证书，然后读取 GET {base}/models 和 GET {base}/_llm/capabilities。单纯的发现不会发出任何 API 请求。

  8. User用户Connect接入

    With a key if the service needs one. The plugin registers a model route in Harness. Conversation requests go straight to POST {base}/responses over HTTPS.

    如果服务需要 key，则带上 key。插件在 Harness 中注册模型路由，对话请求通过 HTTPS 直接发往 POST {base}/responses。

  9. Both sides双方Stay current保持更新

    Changed records replace old ones. A service that stops normally sends a goodbye (TTL 0) and leaves the list within about a second. A service that crashes leaves when its records expire. A network change clears every candidate and starts again from step 3.

    记录变化时替换旧数据。正常停止的服务会发送 goodbye（TTL 为 0），约一秒内从列表中移除；异常退出的服务等记录过期后移除。网络切换时清空所有候选，从第 3 步重新开始。

Candidate validation候选校验

Records go through two stages. Some are never shown at all; others are listed but marked invalid, with the reasons and no base URL.

记录要经过两道关。有些记录根本不会出现在列表中；另一些会被列出，但标记为 invalid，附上原因，且不生成 base URL。

Not listed不会列出

  • The instance does not yet have a PTR, SRV and TXT record and at least one A/AAAA address. The client asks for the missing records and waits; SRV and TXT alone never make a candidate.
  • 实例还没有凑齐 PTR、SRV、TXT 记录和至少一个 A/AAAA 地址。客户端会查询缺少的记录并等待；只有 SRV 和 TXT 不会生成候选。
  • A TXT string is longer than 255 bytes. The record is dropped.
  • 某个 TXT 字符串超过 255 字节，该记录会被丢弃。
  • The packet arrived on an old socket after a network change. It is ignored.
  • 网络切换后从旧 socket 迟到的报文，直接忽略。

Listed as invalid列为无效

  • txtvers, api, scheme or base is missing or empty, or txtvers is not 1.
  • txtvers、api、scheme 或 base 缺失或为空，或 txtvers 不是 1。
  • The profile is not api=openresponses with protovers=2026-04-24, or scheme is not http or https.
  • profile 不是 api=openresponses 加 protovers=2026-04-24，或 scheme 不是 http、https。
  • base breaks the path rules. This implementation also rejects encoded separators (%2F, %5C), encoded dot segments and control characters.
  • base 不符合路径规则。本实现还会拒绝编码后的分隔符（%2F、%5C）、编码后的点段和控制字符。
  • auth is missing for an Open Responses service, because the client cannot tell what the service expects, or it has a value other than required or none.
  • Open Responses 服务缺少 auth（客户端无法判断服务的要求），或其值不是 required、none。
  • The SRV target is not a valid .local host name, the port is outside 1 to 65535, or no address is a valid IP address.
  • SRV 目标不是合法的 .local 主机名，端口不在 1 到 65535 之间，或没有一个地址是合法的 IP 地址。

Trust and API keys信任与 API key

mDNS records on a local network are not authenticated, so the client treats them as untrusted input. The draft requires that credentials or prompts are never sent just because a valid-looking service was found. Trust comes from a separate local document that the service operator provides through a trusted channel.

局域网中的 mDNS 记录没有认证，所以客户端把它们当作不可信输入。草案要求：不能因为发现了一个看起来有效的服务，就发送凭据或提示词。信任来自一份独立的本地文件，由服务运营者通过可信渠道提供。

Checks before any key is sent发送 key 之前的检查

  • The exact base URL is listed in the local trust document.
  • 准确的 base URL 列在本地信任文件中。
  • The discovered addresses overlap the allowed addresses for that entry, and the connection is pinned to them.
  • 发现的地址与该条目允许的地址有交集，连接固定使用这些地址。
  • The certificate chains to the configured CA, matches the advertised host name, and has the expected leaf SHA-256 fingerprint.
  • 证书链到配置的 CA，与公告的主机名匹配，叶证书 SHA-256 指纹符合预期。
  • The advertised auth hint matches the local policy. An announcement cannot downgrade a service from required to none.
  • 公告中的 auth 与本地策略一致。公告不能把服务从 required 降级为 none。
  • HTTP redirects are rejected, so a key is never forwarded to another destination.
  • 拒绝 HTTP 重定向，key 不会被转发到其他目标。
// trust.json, provided by the service operator
{
  "schema": "llm-api-discovery-trust/v1",
  "caFile": "ca.pem",
  "services": [{
    "baseURL": "https://api-office-a.local:8443/v1",
    "allowedAddresses": ["192.168.10.21"],
    "certificateSha256": "<64 hex characters of the leaf certificate DER>",
    "auth": "required"
  }]
}

Saved and session keys are bound to the endpoint, certificate, allowed addresses and auth policy, not to the display name. A same-named service on another network cannot use them. 关于 auth=none。草案的通用 TXT 字段允许 none，但其 Open Responses 绑定（§5.3）要求 auth=required。因此免 key 的 Open Responses 是本项目的本地实验。这类候选会带有 draftAuthCompatible: false 和一条校验警告。

Changing networks网络切换

The client follows whichever local network the device is attached to. This works for any move between local networks: office to home, one lab to another, one building to the next. The discovery client reports its state as one of four values.

客户端跟随设备当前接入的局域网。任意两个局域网之间的切换都一样：公司到家、一个实验室到另一个实验室、一栋楼到另一栋楼。发现客户端用以下四种状态之一报告自身状态。

Automatic network following (interfaceMode: auto) is in the current prereleases: discovery core 0.4.0-roaming.1 and Harness plugin 0.6.0-roaming.1, both bundled with demo 0.7.0-roaming.1. Earlier releases use the configured interface address, or else the first eligible IPv4 interface, without the selection rules and network-change detection described below.

自动跟随网络（interfaceMode: auto）属于当前的预发布版本：发现核心库 0.4.0-roaming.1 和 Harness 插件 0.6.0-roaming.1，两者都随 Demo 0.7.0-roaming.1 提供。更早的正式版使用配置的网卡地址，未配置时使用第一个可用的 IPv4 网卡，没有下面介绍的选择规则和网络变化识别。

Choosing the interface选择网卡

With interfaceMode: auto, the client follows one physical LAN interface at a time, in this order of preference:

设置 interfaceMode: auto 时，客户端一次跟随一张物理网卡，优先顺序如下：

  1. The adapter named in preferredInterfaceName (for example en0), when it has a usable IPv4 address.
  2. preferredInterfaceName 指定的网卡（例如 en0），前提是它有可用的 IPv4 地址。
  3. A physical adapter that carries the default route, by route metric.
  4. 承载默认路由的物理网卡，按路由优先级排序。
  5. The previously selected adapter, if it is still available.
  6. 之前选中的网卡，如果它仍然可用。
  7. A stable name and address order among the remaining physical adapters.
  8. 其余物理网卡按名称和地址的稳定顺序选择。

VPN, container and virtual adapters are skipped. Use interfaceMode: pinned with an interfaceAddress to choose one deliberately. The network is checked every 2 seconds by default.

VPN、容器和虚拟网卡会被跳过。如需明确指定，使用 interfaceMode: pinned 加 interfaceAddress。默认每 2 秒检查一次网络。

Same IPv4 address on two networks两个网络分配了相同的 IPv4 地址

Two networks can give the laptop the same address. The client also reads the default gateway and its cached hardware address, read-only, to notice the change: route and arp on macOS, /proc/net/route and /proc/net/arp on Linux, Get-NetRoute and Get-NetNeighbor on Windows. It needs no location permission and contacts no external service. This is best effort; an app with OS network-change notifications can supply a stronger signal through the resolveNetworkAttachment hook.

两个网络可能给笔记本分配相同的地址。客户端还会以只读方式读取默认网关及其缓存的硬件地址来识别变化：macOS 使用 route 和 arp，Linux 读取 /proc/net/route 和 /proc/net/arp，Windows 使用 Get-NetRoute 和 Get-NetNeighbor。不需要定位权限，也不访问外部服务。这是尽力而为的检测；能收到系统网络变化通知的应用，可以通过 resolveNetworkAttachment 钩子提供更可靠的信号。

A network change never grants trust, moves keys to a new service, switches the conversation's model or replays a request. Interrupted streams end with an availability message.

网络切换不会授予信任，不会把 key 转给新服务，不会更换会话所用的模型，也不会重放请求。被中断的流式请求会以“服务暂不可用”的提示结束。

Advertiser lifecycle公告器生命周期

The advertiser publishes services described in a JSON file, or from inside a Node.js service process. Its status moves through probing, announcing and stopped.

公告器根据 JSON 配置文件发布服务，也可以嵌入 Node.js 服务进程中运行。状态依次为 probing、announcing、stopped。

Field字段 Meaning含义
interfaceAddressIPv4 address of the network interface to announce on.用于发布公告的网卡 IPv4 地址。
ttlRecord lifetime in seconds. Default 120; the CLI accepts 1 to 4500.记录有效期（秒）。默认 120，命令行允许 1 到 4500。
services[].instanceNameUnique instance label, up to 63 bytes. Use hyphens, not dots.唯一的实例名，最长 63 字节。用连字符，不要用点。

  • 未知字段会被拒绝，凭据不会意外进入 TXT。配置文件最大 64 KiB，最多 128 个服务。

  • 按 Ctrl+C 或发送 SIGTERM 会发出 goodbye 记录并关闭 socket。进程被强制结束时，记录在 TTL 到期后失效。
  • The CLI does not watch API health. Stop it when the API stops, or embed the library and call setEnabled(id, false).
  • 命令行不监测 API 健康状态。API 停止时应同时停止公告器，或嵌入库并调用 setEnabled(id, false)。

Discover services in your own client在自己的客户端中发现服务

This example uses discovery core 0.4.0-roaming.1. With release 0.3.2, pass interfaceAddress instead of interfaceMode.

此示例使用发现核心库 0.4.0-roaming.1。使用 0.3.2 正式版时，请用 interfaceAddress 代替 interfaceMode。

import { createDiscoveryClient } from '@llm-discovery/discovery-core';

const client = createDiscoveryClient({
  interfaceMode: 'auto',     // follow the current LAN
  waitForNetwork: true,     // wait quietly when offline
});
client.subscribe(event => {
  if (event.type === 'added' || event.type === 'updated')
    console.log(event.candidate.displayName, event.candidate.baseURL);
});
await client.start();
